# From Failure to Fix: A Practical Guide to Query Enhancement for Arabic Retrieval Using MIRACL

## Overcoming the Metadata Gap: Leveraging NoMIRACL for Nuanced Failure Analysis

A primary challenge in evaluating and improving information retrieval systems, particularly on multilingual benchmarks like MIRACL, is the absence of fine-grained passage-level metadata such as domain or topic labels [[1](https://arxiv.org/pdf/2210.09984), [3](https://www.researchgate.net/publication/373722130_MIRACL_A_Multilingual_Retrieval_Dataset_Covering_18_Diverse_Languages)]. This lack of context makes it difficult to diagnose why a system fails on certain queries; without knowing if a failure occurred in a legal, medical, or historical context, analysis is limited to broad performance metrics. However, recent developments in the field provide a powerful tool to circumvent this limitation. The MIRACL dataset itself was introduced as a benchmark for ad hoc retrieval across 18 languages covering over three billion native speakers [[3](https://www.researchgate.net/publication/373722130_MIRACL_A_Multilingual_Retrieval_Dataset_Covering_18_Diverse_Languages), [21](https://www.sciencedirect.com/science/article/pii/S2949719125000706)], but its utility for deep error analysis has been significantly enhanced by the creation of the NoMIRACL dataset [[28](https://aclanthology.org/2024.findings-emnlp.730.pdf), [83](https://aclanthology.org/2024.findings-emnlp.730/)].

NoMIRACL is not merely an extension of MIRACL; it is a specialized, human-annotated dataset designed specifically to evaluate the robustness of Large Language Models (LLMs) within Retrieval-Augmented Generation (RAG) pipelines [[84](https://arxiv.org/html/2312.11361v1), [86](https://arxiv.org/html/2405.10936v1)]. It provides a set of passages that were explicitly judged by humans as *non-relevant* to a given query, offering a much richer signal than the binary relevance judgments in the original MIRACL dataset [[80](https://arxiv.org/html/2410.01171v1), [95](https://aclanthology.org/2024.wikinlp-1.3.pdf)]. This distinction is critical because it allows for the identification of "hard negatives"—documents that are plausible but incorrect answers—which represent a more subtle and common form of retrieval failure. By incorporating the NoMIRACL annotations, an error analysis can move beyond simply measuring whether a relevant document was retrieved at all. Instead, it can investigate cases where a relevant document exists in the corpus but was outranked by a high-scoring, yet misleading, non-relevant document provided by the NoMIRACL team [[94](https://aclanthology.org/2025.emnlp-main.9.pdf)]. This capability transforms the analysis from a simple pass/fail evaluation into a nuanced investigation of retrieval confidence and ranking quality. The availability of the NoMIRACL dataset and its associated evaluation code is documented on its GitHub repository, making it readily accessible for integration into a research project [[28](https://aclanthology.org/2024.findings-emnlp.730.pdf)].

The analytical power of NoMIRACL stems from its focus on LLM robustness, which directly relates to RAG system performance [[84](https://arxiv.org/html/2312.11361v1)]. In a RAG pipeline, the retrieval component feeds documents to an LLM, which then synthesizes an answer. If the retrieved documents are noisy or contain plausible distractors, the LLM may generate an answer based on incorrect information, leading to a hallucination [[31](https://aclanthology.org/2025.findings-acl.219.pdf)]. Therefore, a retrieval system that frequently retrieves hard negatives is fundamentally flawed for RAG applications. Research using NoMIRACL has shown its value in testing retrieval robustness across 18 typologically diverse languages, providing a standardized way to measure how well models can distinguish true relevance from superficial similarity [[85](https://arxiv.org/abs/2312.11361), [88](https://aclanthology.org/2024.knowllm-1.15.pdf)]. For this project, the primary use of NoMIRACL will be to stratify retrieval failures. Queries can be categorized not just by their overall performance metrics (like Mean Reciprocal Rank), but also by the nature of their top-ranked non-relevant documents. This enables a deeper understanding of failure modes. For example, one could analyze whether queries that retrieve hard negatives from NoMIRACL tend to share specific characteristics, such as being short and ambiguous or having complex morphological structures. This approach effectively creates a pseudo-evaluation framework that goes far beyond the capabilities offered by the original MIRACL dataset alone. The existence of NoMIRACL, alongside other related efforts like BORDIRLINES for cross-lingual evaluation, signals a shift in the research community towards more sophisticated and robust evaluation methodologies for multilingual retrieval [[80](https://arxiv.org/html/2410.01171v1), [95](https://aclanthology.org/2024.wikinlp-1.3.pdf)]. By adopting this richer annotation set, the project can conduct a more insightful error analysis that is directly aligned with the ultimate goal of improving a RAG system through Query Enhancement.

## Primary Strategy: In-Depth Analysis of Query-Side Features for QE Insights

Given the project's focus on Query Enhancement (QE), a primary strategy for error analysis must center on identifying query-side characteristics that consistently lead to retrieval failures. This approach is direct and actionable, as it targets the very input that QE aims to improve. The core hypothesis is that certain types of queries—based on their linguistic properties—are inherently more challenging for retrieval systems, and systematically analyzing these properties can illuminate the most promising avenues for enhancement. This analysis can be performed entirely within the project's constraints of a six-week timeline and Google Colab's computational limits by leveraging lightweight, off-the-shelf tools and simple heuristics rather than training custom models.

The first step is to define and extract a set of meaningful query-side features from the approximately 3,000 Arabic queries in the MIRACL dataset. These features can be engineered using Python libraries and pre-existing NLP tools. Key features to consider include:
*   **Query Length:** The number of tokens or words in a query is a fundamental predictor of ambiguity. Research indicates that many downstream task failures occur in short sentences of 5–10 tokens [[14](https://www.linkedin.com/posts/mahmoudnamnam_arabic-nlp-text-preprocessing-guide-activity-7293354136169803776-2_lX)]. This feature can be easily calculated using basic string splitting operations.
*   **Lexical Ambiguity:** Queries containing polysemous words (words with multiple meanings) are prone to failure. While full-scale semantic disambiguation is computationally expensive, simpler proxies can be effective. For instance, one could leverage lexical databases adapted for Arabic or simply count the number of synonyms for each query term using a dictionary-based approach. The inherent ambiguity in Arabic text, often exacerbated by the lack of diacritics, is a key factor to consider [[62](https://www.researchgate.net/publication/350788763_Arabic_Natural_Language_Processing_for_Qur'anic_Research_A_Systematic_Review)].
*   **Syntactic Complexity:** The grammatical structure of a query can impact retrieval. Although full syntactic parsing of Arabic is resource-intensive, heuristic proxies can be derived from punctuation (e.g., number of commas, question marks) or keyword spotting (e.g., presence of negations like "not" or interrogatives like "why"). These serve as rough indicators of structural complexity.
*   **Morphological Richness (Arabic-Specific):** Modern Standard Arabic's rich morphology means a single root can generate many word forms. This poses a significant challenge for retrieval models that rely on exact token matching. To address this, one can employ Arabic morphological analyzers to extract the root of query words. An analysis could then determine if queries composed of rare roots or those that are morphologically complex are more likely to fail. Furthermore, the effect of diacritic omission can be studied by comparing retrieval performance on queries with and without case endings, a technique explored in studies on Persian text correction [[16](https://arxiv.org/pdf/2407.14795), [63](https://www.academia.edu/144093214/Proceedings_of_the_Third_Arabic_Natural_Language_Processing_Workshop)].
*   **Translation Artifacts:** As a cross-lingual dataset, some MIRACL queries are translations from English. These translations might contain unnatural phrasing or terminology mismatches. Identifying queries that are direct, literal translations can help pinpoint errors stemming from imperfect translation rather than poor retrieval.

Once these features are extracted for each query, they must be correlated with the retrieval system's performance. The Pyserini framework is ideal for this, as it can output detailed result lists (query_id, doc_id, rank, score) for every query against the MIRACL corpus. The analysis workflow would involve running a baseline retriever (e.g., BM25 or a multilingual dense model like XLM-R), calculating per-query performance metrics such as nDCG@10, Recall@10, and Mean Reciprocal Rank (MRR), and then statistically comparing the average performance of different query groups. For example, one could group all queries with fewer than five tokens and compare their mean `Recall@10` against the mean of longer queries. Statistical tests like ANOVA or t-tests can determine if the observed differences in performance are significant. The table below outlines a potential feature engineering plan.

| Feature Category | Specific Feature | Extraction Method / Tool | Relevance to Retrieval |
| :--- | :--- | :--- | :--- |
| **Length & Density** | Token/Word Count | Python `len()` on split text | Short queries (<10 tokens) are often ambiguous [[14](https://www.linkedin.com/posts/mahmoudnamnam_arabic-nlp-text-preprocessing-guide-activity-7293354136169803776-2_lX)]. |
| **Ambiguity** | Polysemy Proxy | Count synonyms using a lexical database (e.g., AraPyNet) | Queries with multiple meanings are harder to interpret correctly. |
| **Complexity** | Syntactic Simplicity Heuristic | Count of question marks, conjunctions | Complex sentence structures can confuse retrievers. |
| **Morphology** | Root Frequency | Use of an Arabic morphological analyzer (e.g., ARABICA) | Rare roots may correspond to out-of-vocabulary terms. |
| **Orthography** | Diacritic Presence/Absence | Manual annotation or simple regex | Lack of diacritics introduces ambiguity [[62](https://www.researchgate.net/publication/350788763_Arabic_Natural_Language_Processing_for_Qur'anic_Research_A_Systematic_Review)]. |
| **Origin** | Translation Type | Keyword spotting ("translation_of_") | Direct translations may contain unnatural phrasing. |

This structured, quantitative analysis will produce actionable insights. For instance, if the analysis reveals that queries with morphologically complex roots have a significantly lower `nDCG@10`, the next logical step in the project would be to implement a Query Enhancement technique focused on normalizing query forms, such as expanding queries based on their constituent roots before retrieval. This methodical approach ensures that development effort is directed toward solving the most prevalent problems identified by empirical data.

## Secondary Strategy: Analyzing Retrieval Result Patterns to Identify Systemic Failures

Beyond examining the queries themselves, a second layer of analysis involves scrutinizing the patterns within the retrieval results generated by the system. This secondary strategy is crucial because it reveals systemic weaknesses in the retrieval algorithm, regardless of the query's inherent difficulty. By analyzing the structure of the ranked list of documents, one can identify common "failure modes" that suggest where Query Enhancement (QE) or reranking strategies would be most beneficial. These analyses can be conducted efficiently using Python libraries like `pandas` for data manipulation and `matplotlib` or `seaborn` for visualization, fitting well within the project's resource constraints.

One of the most informative analyses is the examination of **rank distributions**. Specifically, plotting the distribution of the rank of the first relevant document (`R1`) for all queries can provide a clear picture of the nature of failures. A large number of failures occurring at very low ranks (e.g., the relevant document is missed entirely, `R1` is infinity) suggests catastrophic failure, perhaps due to severe query ambiguity or a poor initial retrieval model. Conversely, a high frequency of `R1` values just outside the top-K results (e.g., rank 11-50) points to a problem with the ranking function itself, indicating that the system finds relevant documents but fails to promote them adequately. This pattern strongly suggests that a two-stage retrieval architecture, involving a fast initial retrieval followed by a more computationally intensive re-ranking phase, could be highly effective [[47](https://aclanthology.org/2025.mrl-main.42.pdf)].

Another powerful metric is the **score gap**, which measures the difference in relevance scores between the highest-scoring relevant document and the highest-scoring non-relevant document within the top-K results for a given query. A small score gap indicates a "noisy" retrieval environment where relevant documents are difficult to distinguish from plausible distractors. Such cases represent prime opportunities for QE. A well-designed enhancement strategy, such as adding more discriminative keywords or reformulating the query to be more specific, could widen this score gap and pull the correct document higher in the ranking. Calculating and visualizing the distribution of these score gaps across all queries can quantify the prevalence of this issue.

The most advanced pattern analysis leverages the **hard negative analysis** made possible by the NoMIRACL dataset. Hard negatives are passages that are semantically similar to the query but do not contain the correct answer [[93](https://aclanthology.org/2024.acl-long.540.pdf)]. By comparing the embeddings or scores of relevant passages against the human-annotated non-relevant passages from NoMIRACL, one can identify the specific types of distractors that the model is most susceptible to [[94](https://aclanthology.org/2025.emnlp-main.9.pdf)]. This provides concrete, qualitative examples of failure. For instance, if a query about "the causes of World War I" frequently retrieves a hard negative passage about "major alliances in Europe," it indicates a semantic mismatch that could be addressed by a QE module trained to better handle temporal or causal relationships. This type of analysis moves beyond abstract metrics to provide tangible evidence of the model's reasoning flaws. The following table summarizes these retrieval pattern analysis techniques.

| Analysis Technique | Metric/Visualization | Purpose | Tools/Libraries |
| :--- | :--- | :--- | :--- |
| Rank Distribution Analysis | Histogram of `Rank` of First Relevant Document (`R1`) | Distinguish between catastrophic misses and near-misses. | `pandas`, `matplotlib` |
| Score Confidence Analysis | Box plot of score gap (Top Non-Relevant Score - Top Relevant Score) | Quantify retrieval confidence and identify cases where relevant docs are hard to distinguish from distractors. | `pandas`, `seaborn` |
| Hard Negative Analysis | Manual inspection of top results containing passages from NoMIRACL | Identify specific types of plausible-but-wrong documents that fool the retriever. | Custom script, pandas |
| Embedding Similarity Analysis | Distribution plots of cosine similarity between query and top-K passages | Visualize the signal-to-noise ratio in retrieval; successful cases show sharp peaks, failed cases show flat distributions. | `scikit-learn`, `matplotlib` |

Finally, **embedding similarity analysis** offers another perspective. By plotting the distribution of cosine similarities between the query's embedding and the embeddings of the top-K retrieved passages, one can visualize the retrieval landscape. Successful retrievals typically exhibit a sharp peak corresponding to the relevant documents, while failed retrievals often show a broad, flat distribution, indicating no clear signal. Comparing these distributions for queries that succeed versus those that fail can reveal fundamental differences in how the retrieval model processes different query types. Together, these pattern analyses provide a comprehensive view of the retrieval system's behavior, complementing the query-side feature analysis and forming a robust foundation for developing targeted Query Enhancement strategies.

## Tertiary Strategy: Lightweight Unsupervised Clustering as a Pseudo-Metadata Source

While the primary focus of the project is on query-side features and retrieval patterns, the absence of explicit passage metadata remains a significant hurdle. To partially address this, a tertiary strategy involving lightweight, unsupervised clustering can be employed to create a coarse-grained topic labeling system. This approach does not aim to build a perfect, comprehensive taxonomy but rather to generate sufficient structure to allow for rudimentary topic-based error analysis. Given the project's constraints of limited compute on Google Colab and a tight timeline, this method must be implemented efficiently.

The core idea is to use a pre-trained multilingual embedding model to convert all MIRACL passages into numerical vectors (embeddings). These embeddings capture semantic meaning, allowing semantically similar passages to be grouped together in vector space. Subsequently, a computationally efficient clustering algorithm, such as K-Means, can be applied to partition the passages into a predefined number of clusters (topics). The feasibility of this approach hinges on managing the scale of the task. Processing all ~2.1 million passages is computationally prohibitive. However, several strategies can drastically reduce the workload. One effective method is **downsampling**, which involves selecting a representative subset of the passages for clustering [[27](https://openreview.net/pdf/2764d0a4218a3dcedc9d41e861bbd8cccd47e717.pdf)]. Another is to cluster only the passages that were ever retrieved by the baseline system for at least one query in the MIRACL test set; this reduces the dataset from millions to potentially tens or hundreds of thousands of documents. Caching the computed embeddings is also a crucial optimization to prevent redundant calculations [[27](https://openreview.net/pdf/2764d0a4218a3dcedc9d41e861bbd8cccd47e717.pdf)].

For the embedding model, several lightweight yet effective options are available. Multilingual models like mBERT and XLM-R have demonstrated strong performance across a wide range of languages [[52](https://arxiv.org/html/2412.12591v2)]. More recent models like the E5-NL series offer compact yet efficient embedding capabilities [[69](https://www.researchgate.net/publication/395541274_MTEB-NL_and_E5-NL_Embedding_Benchmark_and_Models_for_Dutch), [70](https://arxiv.org/pdf/2509.12340)]. Even newer Arabic-centric models like the Swan family could be considered, though they may require more resources [[2](https://aclanthology.org/2025.findings-naacl.263.pdf)]. For this project, starting with a smaller variant of XLM-R or E5-NL would be a pragmatic choice. Once the embeddings are generated for the sampled passages, K-Means clustering can be performed using the `scikit-learn` library in Python, which is both lightweight and easy to integrate into a Pyserini-based workflow.

After clustering, the final and most important step is manual inspection. A researcher should examine a random sample of passages from each resulting cluster. By reading a few dozen documents from a cluster, descriptive labels such as "Sports," "Technology," "History," or "Science" can be assigned. These labels serve as pseudo-domain tags. With these tags in place, the error analysis can be enriched. For example, one could ask: "Are retrieval failures for short, ambiguous queries (from the primary analysis) concentrated in a particular inferred topic?" or "Do cases with small score gaps predominantly occur when retrieving documents from 'Medical' or 'Legal' clusters?" This allows the analysis to transcend purely lexical or structural factors and begin to incorporate semantic content, even in a coarse-grained manner. While this clustering-based approach requires more effort than the primary query-side analysis, it offers a valuable way to partially overcome the metadata deficit. It should be treated as an advanced optional step, to be undertaken only if time permits after completing the more direct and impactful query-side and pattern analyses.

## Actionable Recommendations for Query Enhancement Strategies

The ultimate goal of this error analysis is to inform the design of targeted Query Enhancement (QE) techniques. By synthesizing the findings from the query-side feature analysis and the retrieval result pattern analysis, it becomes possible to formulate specific, evidence-based hypotheses about how to improve the retrieval system. The recommendations below are grounded in the anticipated outcomes of the proposed analytical steps and are designed to be practical and implementable within the project's constraints.

Based on the expected finding that short, ambiguous queries are a major source of failure, one of the most promising QE strategies is **synonym-based query expansion**. If the analysis shows a strong correlation between short query length and poor retrieval performance (e.g., low `Recall@10`), it suggests that the original query lacks sufficient discriminative terms. A lightweight QE module can be developed to automatically expand these short queries by appending synonyms for the existing terms. For Arabic, this would require an Arabic synonym dictionary or a tool that can find related terms. The expanded query, now longer and potentially more specific, can then be used to perform a new retrieval run, either as a rerank of the original results or as a primary retrieval. This directly addresses the identified weakness.

A second recommendation stems from the analysis of retrieval result patterns, particularly the identification of small score gaps and frequent misranking of hard negatives. This indicates a need for improved retrieval confidence and discrimination. Here, a **two-stage retrieval architecture** is a highly relevant strategy. In this setup, the first stage uses a fast, non-interpretable model like BM25 to produce a large candidate set (e.g., top 1000 documents). The second stage then applies a more powerful, light-weight re-ranker, such as a pre-trained multilingual model (e.g., miniLM, or a distilled version of XLM-R), to re-score and re-order the candidate set. This approach is effective because it separates the broad search from the fine-grained discrimination, a pattern seen in advanced reranker research [[47](https://aclanthology.org/2025.mrl-main.42.pdf)]. The re-ranker can better understand the semantic nuances needed to distinguish a relevant document from a hard negative, thereby widening the score gap and promoting the correct document higher in the final ranking.

Third, if the analysis of morphological features reveals that queries with rare roots or complex inflections consistently fail, a **query normalization and root-based expansion** strategy should be explored. This involves preprocessing the query using an Arabic morphological analyzer to extract the root of each word. The normalized query can then be used for retrieval. Additionally, a synonym dictionary or a thesaurus can be used to find other words sharing the same root and append them to the query. This technique helps bridge the vocabulary gap between the user's query and the surface form of the relevant passage text, addressing a core challenge in Arabic Information Retrieval [[64](https://core.ac.uk/download/pdf/1146154.pdf)]. Recent work on improving multilingual retrieval via post-hoc editing of embeddings also points to the importance of focusing on the semantic content rather than surface forms, reinforcing the value of this approach [[25](https://arxiv.org/html/2601.04768v1)].

Finally, the combination of all analyses may point to a more general need for **dynamic query rewriting**. Instead of applying a single enhancement strategy to all queries, the system could be designed to select the appropriate QE technique based on the query's profile. For instance, a classifier (which could be a simple rule-based system initially) could categorize a new query as "short/ambiguous," "morphologically complex," or "high-confidence." The system would then route the query to the corresponding enhancement module. This dynamic approach is more sophisticated but offers the greatest potential for improvement. The following table summarizes these actionable recommendations.

| Identified Failure Mode | Recommended Query Enhancement Strategy | Description | Implementation Difficulty |
| :--- | :--- | :--- | :--- |
| Short, Ambiguous Queries | Synonym-Based Query Expansion | Append synonyms to the original query to increase its discriminative power. | Low |
| Small Score Gaps / Hard Negatives | Two-Stage Retrieval with a Light-Weight Re-ranker | Use a fast retriever (BM25) for initial recall, followed by a powerful model (e.g., miniLM) for fine-grained re-ranking. | Medium |
| Morphologically Complex/Rare Roots | Query Normalization and Root-Based Expansion | Extract roots from query words and expand the query with other words sharing the same root. | Medium |
| General Poor Performance | Dynamic Query Rewriting | Implement a rule-based or simple ML classifier to select the best QE strategy for each incoming query. | High |

These recommendations provide a clear roadmap from error analysis to solution. They are directly linked to the anticipated findings of the project's analytical phases and prioritize lightweight, off-the-shelf components over custom model training, ensuring feasibility within the project's timeline and resource constraints.

## Synthesis and Project Implementation Roadmap

This research report has outlined a comprehensive and practical methodology for conducting error analysis on Arabic retrieval systems using the MIRACL dataset, specifically addressing the challenge of missing passage-level metadata. The central insight is that even without explicit domain labels, a multi-faceted analysis combining query-side features, retrieval result patterns, and lightweight clustering can yield deep, actionable insights. The integration of the NoMIRACL dataset is paramount, as it provides the necessary nuance to move beyond simple relevance judgments and analyze the critical problem of hard negatives. The proposed strategies prioritize lightweight, off-the-shelf tools and simple heuristics, making them eminently suitable for implementation within the six-week timeline and Google Colab's compute environment. The ultimate objective is to translate these analytical findings into a set of targeted Query Enhancement (QE) techniques, creating a direct and impactful contribution to the project.

To ensure timely and effective execution, the project should follow a structured, phased implementation roadmap. This plan breaks down the six-week timeline into manageable stages, prioritizing the most impactful analyses first and treating more computationally intensive tasks as optional.

**Phase 1: Setup and Baseline Evaluation (Week 1)**
The initial week should be dedicated to establishing the foundational infrastructure. This includes setting up a Jupyter notebook environment in Google Colab, installing necessary libraries like Pyserini, `pandas`, `scikit-learn`, and `matplotlib`. The MIRACL Arabic dataset and the NoMIRACL annotations must be downloaded and prepared [[28](https://aclanthology.org/2024.findings-emnlp.730.pdf)]. A strong baseline retrieval model should be selected and run against the MIRACL corpus. It is recommended to use a robust multilingual model like XLM-R or a proven sparse model like BM25. The complete output of the retrieval run, including query IDs, document IDs, ranks, and scores for all results, must be saved to disk. This serves as the raw data for all subsequent analysis.

**Phase 2: Primary Analysis - Query-Side Feature Correlation (Week 2)**
In the second week, the focus shifts to the primary strategy of analyzing query-side features. Scripts must be developed to parse each of the ~3000 MIRACL Arabic queries and extract the engineered features discussed previously: length, syntactic complexity heuristics, and potentially root information using an Arabic morphological analyzer. Concurrently, per-query retrieval performance metrics such as `nDCG@10`, `Recall@10`, and `MRR` should be calculated. The core of this phase is the statistical analysis, using tools like `scipy` to perform tests that correlate each query feature with the performance metrics. The outcome of this phase should be a clear report identifying which query characteristics are the most significant predictors of retrieval success or failure.

**Phase 3: Secondary Analysis - Retrieval Result Patterns (Week 3)**
The third week focuses on the secondary strategy of analyzing retrieval result patterns. Code should be written to calculate and visualize key metrics: the distribution of the rank of the first relevant document, the distribution of score gaps between top relevant and non-relevant documents, and a systematic analysis of the hard negatives present in the NoMIRACL set. The goal is to create a series of figures and tables that illustrate the typical "failure modes" of the baseline system. This visual and quantitative summary is crucial for understanding the systemic weaknesses of the retrieval pipeline.

**Phase 4: Tertiary Analysis (Optional) - Lightweight Clustering (Week 4)**
If the primary and secondary analyses are completed ahead of schedule, this week can be used for the optional tertiary analysis. A representative subset of the MIRACL passages should be sampled. Multilingual embeddings for these passages should be generated using a lightweight model like E5-NL. K-Means clustering can then be applied to group the passages into a reasonable number of clusters (e.g., 50-100). After manually inspecting the clusters to assign descriptive topic labels, these labels can be cross-referenced with the findings from the previous weeks to see if failure patterns are concentrated in specific inferred domains.

**Phase 5: Synthesis and QE Strategy Formulation (Week 5)**
With all analytical data collected, the fifth week is for synthesis. The findings from all three analytical phases must be integrated into a coherent narrative that explains the dominant reasons for retrieval failure. Based on this unified understanding, 2-3 specific and targeted Query Enhancement strategies should be formulated, drawing directly from the recommendations provided in this report (e.g., synonym expansion, two-stage retrieval).

**Phase 6: Refinement and Reporting (Week 6)**
The final week should be used to briefly prototype one or two of the proposed QE techniques to validate their potential effectiveness. This could involve writing a small script to apply query expansion and re-running the retriever on a subset of queries to observe any improvements in metrics like `Recall@10`. The culmination of the project will be a final research report that clearly articulates the error analysis methodology, presents the key findings supported by data and visualizations, and justifies the recommended Query Enhancement strategies. This structured approach ensures that the project progresses logically from data preparation to actionable insight, maximizing the chances of success within the given constraints.
